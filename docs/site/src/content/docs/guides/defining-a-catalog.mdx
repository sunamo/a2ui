import {Aside, Tabs, TabItem} from '@astrojs/starlight/components';

Define a custom A2UI catalog by writing a `catalog.json` schema file, loading it on your agent, and registering matching UI widgets on your client app under the same `catalogId`.

## When you need a catalog.json file

If your agent and client share the same language and repository, you can define component schemas directly in code. Write a standalone `catalog.json` file when your backend agent and client app use different languages (for example, a Python agent serving a Flutter, React, or SwiftUI app) or when you publish a reusable catalog for other teams.

In A2UI v1.0, your catalog works alongside the built-in [basic catalog](/specification/v1.0/schemas/#basic_catalog.json), so you keep standard layout widgets (`Column`, `Row`, `Text`, `Button`) and define only the custom widgets unique to your app. See [Catalogs](/concepts/catalogs/) for how catalog negotiation works at runtime.

## Step 1: Create a minimal catalog.json

Create a file named `status_catalog.json` that defines a single `StatusBadge` component with two properties: a bindable `label` string and a `status` tone.

```json
  "$id": "https://example.com/catalogs/status/v1/catalog.json",

          "type": "string",

        }
      },

    }
  },
  "$defs": {
    "anyComponent": {
      "oneOf": [{"$ref": "#/components/StatusBadge"}],
      "discriminator": {"propertyName": "component"}

    "anyFunction": {"not": {}}
  }
}
```

| Field             | Purpose                                                                                                                                                                                                                                                                                                                          |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `catalogId`       | Unique URI shared by the agent and client renderer. Version the URI path (`v1/`, `v2/`) when making breaking changes.                                                                                                                                                                                                            |
| `protocolVersion` | Wire version (`"1.0"`, without a leading `v`) validated against [`catalog_definition.json`](/specification/v1.0/schemas/#catalog_definition.json). Omitted in v0.9.1 standalone files.                                                                                                                                           |
| `components`      | Map of component schemas. Referencing `DynamicString` lets `label` accept either literal text or a data-model binding (`{"@path": "/statusText"}` in v1.0; `{"path": "/statusText"}` in v0.9.1). In v0.9.1, components also compose [`ComponentCommon`](/specification/v0.9.1/schemas/#common_types.json/$defs/ComponentCommon). |
| `$defs`           | Declares `anyComponent` (union of all components) and `anyFunction` (`{"not": {}}` when the catalog defines no custom functions).                                                                                                                                                                                                |

## Step 2: Load the catalog on your agent

Load `status_catalog.json` with `Catalog.fromJson` (`Catalog.from_json` in Python) and pass it to `A2uiGenerator` alongside the basic catalog. `A2uiGenerator` automatically includes your component schema in the LLM prompt and validates generated messages against it.

<Tabs syncKey="sdk-lang">
  <TabItem label="TypeScript">

```typescript
import {readFileSync} from 'node:fs';

import {A2uiGenerator, CatalogConfig, ExpressFormatFactory} from '@a2ui/agent';
import {Catalog} from '@a2ui/web_core';
import {basicCatalog} from '@a2ui/web_core/v1_0';

const statusCatalog = Catalog.fromJson(JSON.parse(readFileSync('./status_catalog.json', 'utf8')));

export const generator = new A2uiGenerator(
  [new CatalogConfig(basicCatalog), new CatalogConfig(statusCatalog)],
  undefined,
  new ExpressFormatFactory(),
);
```

  </TabItem>

## Step 3: Register the widget on your client

Implement `StatusBadge` in your UI framework, wrap it in a `Catalog` with the same `catalogId` (`https://example.com/catalogs/status/v1/catalog.json`), and register it alongside the basic catalog in `MessageProcessor` (or `provideA2UI` in Angular).

<Tabs syncKey="renderer-framework">
  <TabItem label="Flutter">

```dart
import 'package:a2ui_core/a2ui_core.dart';
import 'package:a2ui_flutter/a2ui_flutter.dart';
import 'package:a2ui_flutter/basic_catalog.dart';
import 'package:flutter/material.dart';
import 'package:json_schema_builder/json_schema_builder.dart';

final statusBadge = ComponentImplementation(
  name: 'StatusBadge',
  schema: Schema.object(
    properties: {
      'component': Schema.string(enumValues: ['StatusBadge']),
      'label': CommonSchemasV1.dynamicString,
      'status': Schema.string(enumValues: ['info', 'success', 'warning']),
    },
    required: ['component', 'label', 'status'],
  ),
  builder: (context, node, props, buildChild) {
    final String label = props.string('label') ?? '';
    final String status = props.string('status') ?? 'info';
    return Chip(label: Text('$status: $label'));
  },
);

final statusCatalog = Catalog<ComponentImplementation, FunctionImplementation>(
  id: 'https://example.com/catalogs/status/v1/catalog.json',
  protocolVersion: A2uiProtocolVersion.v1_0,
  components: [statusBadge],
);

final processor = MessageProcessor(catalogs: [basicCatalog(), statusCatalog]);
```

## Advanced catalog features

Expand the sections below when your catalog needs custom functions or input validators, structural layout rules, prompt instructions, or automated CI parity tests.

<details>
<summary>Adding custom functions and input validators to your catalog</summary>

Add a `functions` map to `catalog.json` when surfaces need custom formatters, computed values, or input validation rules:

1. In v1.0, each [`FunctionDefinition`](/specification/v1.0/schemas/#catalog_definition.json/$defs/FunctionDefinition) declares `returnType` (`"string"`, `"number"`, `"boolean"`, `"array"`, `"object"`, `"validationResult"`, `"any"`, or `"void"`) at the top level of the function object and uses `"@call"` inside `properties`. Validation functions used in `checks` return `"validationResult"` so they can produce structured [`ValidationResult`](/specification/v1.0/schemas/#catalog_definition.json/$defs/ValidationResult) objects (`{"valid": false, "message": "..."}`).
2. v1.0 functions can set `allowedCallers` to `"rendererOnly"` (default), `"agentOnly"`, or `"rendererOrAgent"`. Side-effecting `"rendererOnly"` functions (such as opening external URLs) can also set `"requiresUserActivation": true` so they run only from user-triggered actions.
3. In v0.9.1 standalone files, functions place `"call"` and `"returnType": {"const": "..."}` inside `properties`, and validation rules return `"boolean"`. When a v0.9.1 renderer advertises inline catalogs in `a2uiClientCapabilities`, `MessageProcessor` converts the `functions` map into the array format defined by [`client_capabilities.json`](/specification/v0.9.1/schemas/#client_capabilities.json/$defs/FunctionDefinition).

On the client, register matching `FunctionImplementation` objects on your `Catalog` (shown here in TypeScript with `createFunctionImplementation`; Dart and Swift provide matching `FunctionImplementation` types in `a2ui_core` and `A2UICore`):

```typescript
import {z} from 'zod';

import {Catalog, DynamicNumberSchema, createFunctionImplementation} from '@a2ui/web_core/v1_0';

const discountedPriceFn = createFunctionImplementation(
  {
    name: 'discountedPrice',
    returnType: 'number',
    allowedCallers: 'rendererOrAgent',
    schema: z.object({price: DynamicNumberSchema, percentOff: DynamicNumberSchema}),
  },
  ({price, percentOff}) => Number((Number(price) * (1 - Number(percentOff) / 100)).toFixed(2)),
);

const validDiscountFn = createFunctionImplementation(
  {
    name: 'validDiscount',
    returnType: 'validationResult',
    allowedCallers: 'rendererOnly',
    schema: z.object({percentOff: DynamicNumberSchema}),
  },
  ({percentOff}) => {
    const pct = Number(percentOff);
    return pct >= 0 && pct <= 70
      ? {valid: true}
      : {valid: false, message: 'Discount must be between 0% and 70%.'};
  },
);

export const pricingCatalog = new Catalog(
  'https://example.com/catalogs/pricing/v1/catalog.json',
  '1.0',
  [],
  [discountedPriceFn, validDiscountFn],
);
```

<summary>Layout rules, child slots, actions, input checks, and prompt instructions</summary>

Beyond scalar properties, [`catalog_definition.json`](/specification/v1.0/schemas/#catalog_definition.json) supports structural constraints, interactive slots, and LLM prompt guidance:

1. Constrain component hierarchy in v1.0 with `allowedParents` (for example, `["Column", "List"]`, or `["Surface"]` for root-only modals) and `allowedChildren` (`["Button"]`) on a [`ComponentDefinition`](/specification/v1.0/schemas/#catalog_definition.json/$defs/ComponentDefinition). `"Surface"` is reserved and cannot be used as a component name, and v1.0 identifiers must follow Unicode UAX #31 without a leading `@`.
2. Reference [`ChildList`](/specification/v1.0/schemas/#common_types.json/$defs/ChildList) or `ComponentId` for nested component slots, [`Action`](/specification/v1.0/schemas/#common_types.json/$defs/Action) for event dispatches or local mutations, and compose [`Checkable`](/specification/v1.0/schemas/#common_types.json/$defs/Checkable) via `allOf` when a component accepts client-side `checks`.
3. Add top-level `instructions` (Markdown appended to the LLM system prompt by `A2uiGenerator`) and `metadata.extensions` (custom metadata keyed by UAX #31 identifiers) in v1.0, or `$defs.theme` in v0.9.1 for catalog-level theme tokens.
4. Put reusable scalar or enum schemas under `$defs`. In v1.0, `$ref` targets inside a catalog may point only to `#/...`, `common_types.json`, or `catalog.json`, and any `$defs` block must include `anyComponent` and `anyFunction` alongside leaf definitions.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.com/catalogs/shop/v1/catalog.json",
  "catalogId": "https://example.com/catalogs/shop/v1/catalog.json",
  "protocolVersion": "1.0",
  "instructions": "Place `ProductCard` inside `Column` or `List` and pass `Button` IDs to `actions`.",
  "metadata": {
    "extensions": {
      "storefrontOwner": "commerce-ui"
    }
  },
  "components": {
    "ProductCard": {
      "type": "object",
      "allowedParents": ["Column", "List"],
      "allowedChildren": ["Button"],
      "allOf": [{"$ref": "common_types.json#/$defs/Checkable"}],
      "properties": {
        "component": {"const": "ProductCard"},
        "name": {"$ref": "common_types.json#/$defs/DynamicString"},
        "price": {"$ref": "common_types.json#/$defs/DynamicNumber"},
        "badge": {"$ref": "#/$defs/BadgeTone"},
        "actions": {"$ref": "common_types.json#/$defs/ChildList"},
        "onSelect": {"$ref": "common_types.json#/$defs/Action"}
      },
      "required": ["component", "name", "price"]
    }
  },
  "$defs": {
    "BadgeTone": {
      "type": "string",
      "enum": ["sale", "new", "limited"]
    },
    "anyComponent": {
      "oneOf": [{"$ref": "#/components/ProductCard"}],
      "discriminator": {"propertyName": "component"}
    },
    "anyFunction": {"not": {}}
  }
}
```

<summary>Testing client-server schema parity in CI</summary>

When your backend agent loads `status_catalog.json` and your client defines schemas in code (with Zod, `json_schema_builder`, or `JSONSchema`), avoid comparing serialized JSON files as raw strings. Code-built schemas and hand-authored JSON files often differ in key order, `$schema` or `instructions` fields, and localized `#/$defs/...` pointers inside `validationSchema`.

Instead, load `status_catalog.json` with `Catalog.fromJson` (`Catalog.from_json` in Python) in a unit test and compare the normalized `Catalog` properties (`id`, `protocolVersion`, component names, `allowedParents`/`allowedChildren`, and function `returnType`/`allowedCallers`) against your client catalog.

```typescript
import assert from 'node:assert/strict';
import {readFileSync} from 'node:fs';
import {test} from 'node:test';

import {Catalog} from '@a2ui/web_core';

import {statusCatalog} from './status_catalog.js';

test('client statusCatalog matches status_catalog.json', () => {
  const specCatalog = Catalog.fromJson(JSON.parse(readFileSync('./status_catalog.json', 'utf8')));

  assert.equal(statusCatalog.id, specCatalog.id);
  assert.equal(statusCatalog.protocolVersion, specCatalog.protocolVersion);
  assert.deepEqual(
    [...statusCatalog.components.keys()].sort(),
    [...specCatalog.components.keys()].sort(),
  );

  for (const [name, specComp] of specCatalog.components) {
    const clientComp = statusCatalog.components.get(name)!;
    assert.deepEqual(clientComp.allowedParents, specComp.allowedParents);
    assert.deepEqual(clientComp.allowedChildren, specComp.allowedChildren);
  }
});
```

```python
import json
from pathlib import Path

from a2ui.core import Catalog
from my_app.catalog import code_status_catalog


def test_status_catalog_parity() -> None:
    spec_catalog = Catalog.from_json(
        json.loads(Path("./status_catalog.json").read_text(encoding="utf-8"))
    )

    assert code_status_catalog.catalog_id == spec_catalog.catalog_id
    assert code_status_catalog.protocol_version == spec_catalog.protocol_version
    assert set(code_status_catalog.components) == set(spec_catalog.components)

    for name, spec_comp in spec_catalog.components.items():
        code_comp = code_status_catalog.components[name]
        assert code_comp.allowed_parents == spec_comp.allowed_parents
        assert code_comp.allowed_children == spec_comp.allowed_children
        assert set(code_comp.parameters.get("properties", {})) == set(
            spec_comp.parameters.get("properties", {})
        )
```

```dart
import 'dart:convert';
import 'dart:io';

import 'package:a2ui_core/a2ui_core.dart';
import 'package:my_app/status_catalog.dart';
import 'package:test/test.dart';

void main() {
  test('Flutter statusCatalog matches status_catalog.json', () {
    final CatalogApi specCatalog = Catalog.fromJson(
      jsonDecode(File('./status_catalog.json').readAsStringSync())
          as Map<String, Object?>,
    );

    expect(statusCatalog.id, specCatalog.id);
    expect(statusCatalog.protocolVersion, specCatalog.protocolVersion);
    expect(
      statusCatalog.components.keys.toSet(),
      specCatalog.components.keys.toSet(),
    );

    for (final MapEntry<String, ComponentApi> entry
        in specCatalog.components.entries) {
      final ComponentImplementation clientComp =
          statusCatalog.components[entry.key]!;
      expect(clientComp.allowedParents, entry.value.allowedParents);
      expect(clientComp.allowedChildren, entry.value.allowedChildren);
    }
  });
}
```
